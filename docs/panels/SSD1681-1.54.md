# Driving the SSD1681 fast — Watchy 1.54", measured

Reference for the SSD1681 on GDEH0154D67 (HINK-E154A07-A1), 200×200 mono, on a
XIAO ESP32-S3. Everything here was measured on glass on 2026-08-20 with
`calib` / `seqscan` / `blink` in `ports/ssd1681-154/firmware/inkvideo_154.cpp`. Companion to
``SSD1683-crowpanel-5.79.md``, which established
the method — the timing law, the null-LUT probe and the activate-byte scan are
all from there.

**Headline: the vendor OTP partial costs 363 ms and gives contrast 97. A
9-frame custom waveform costs 72 ms and gives contrast 121 — better ink, 5x
faster. Streamed and measured: 2.8 fps to 13.0 fps at drive 8, 22.2 at drive 4,
34.5 at drive 2.** The 5.79" reaches 16 fps on video with 5.4x more pixels; this
panel passes that.

Nothing here is a trick of measurement. Timing is the BUSY pin. Image quality is
the 8MP camera through `tools/panelshot.py`, measured inside a calibrated active
area, not eyeballed.

---

## 1. The timing law

```
group bytes = [TPA, TPB, SRAB, TPC, TPD, SRCD, RP]
frames      = (RP+1) * ( (SRAB+1)*(TPA+TPB) + (SRCD+1)*(TPC+TPD) )
busy        = frames * frame_period
```

With EOPT `0x07` and a rails-up activate byte **that is the whole equation** —
no fixed cost, no extra frame.

**Every repeat field is n+1: a stored 0 runs the group ONCE.** That one fact is
what makes the vendor tables decode, and it is the single easiest thing to get
wrong, because a wrong repeat interpretation leaves BUSY perfectly linear while
the waveform runs 2x or 4x longer than intended. The error hides in plain sight.

### How it was settled — `bytescan`

Perturbing one group-0 byte at a time from a baseline of `1,8,0,0,0,1,0`
(9 frames), probe value 4:

| byte | table | frames | which field |
|------|-------|--------|-------------|
| — | 1,8,0,0,0,1,0 | 9 | baseline |
| 0 | 4,8,0,0,0,1,0 | 12 | TPA (additive) |
| 1 | 1,4,0,0,0,1,0 | 5 | TPB (additive) |
| 2 | 1,8,4,0,0,1,0 | 45 | SRAB (x5, so n+1) |
| 3 | 1,8,0,4,0,1,0 | 17 | TPC (additive, x2 because SRCD=1 means 2) |
| 4 | 1,8,0,0,4,1,0 | 17 | TPD, same |
| 5 | 1,8,0,0,0,4,0 | 9 | SRCD (no effect: TPC=TPD=0) |
| 6 | 1,8,0,0,0,1,4 | 45 | RP (x5, so n+1) |

Only the law above reproduces all seven. It then retro-predicted two earlier
surprises **exactly**, which is the real confirmation:

- a null table of `tp,0,1,0,0,0,1` had measured `4 x tp` frames. Decoded:
  RP=1→2, SRAB=1→2, so `2 * (2*tp) = 4tp`. ✓
- the first real waveform, `1,0,5,1,0,1,1`, measured 15.94 frames. Decoded:
  RP=1→2, SRAB=5→6, SRCD=1→2, so `2 * (6*1 + 2*1) = 16`. ✓

And it holds across the whole shipped range — predicted vs measured busy at
drive 1/2/3/4/6/8/12/16/24: 16/24/32/40/56/72/104/137/201 ms against
16/24/32/40/56/72/104/137/201 ms. Exact at every point.

### frame_period — from the FR field, LUT bytes 144..149

Measured by sweeping TP under a null waveform (§5):

| FR code | nominal | measured us/frame | 1/period |
|---------|---------|-------------------|----------|
| `0x01` | 25 Hz | 40321 | 24.8 Hz |
| `0x09` | 37.5 Hz | 26862 | 37.2 Hz |
| `0x02` | 50 Hz | 20159 | 49.6 Hz |
| `0x0A` | 62.5 Hz | 16118 | 62.0 Hz |
| `0x03` | 75 Hz | 13437 | 74.4 Hz |
| `0x0B` | 87.5 Hz | 11508 | 86.9 Hz |
| **`0x04`** | **100 Hz** | **10080** | **99.2 Hz** |
| `0x0C` | 112.5 Hz | 8953 | 111.7 Hz |
| `0x05` | 125 Hz | 8063 | 124.0 Hz |

All nine measured here. Every code lands 0.8 % low — one clock offset, not
scatter. **The SSD1681 shares the SSD1683's FR table**, both runs of it: 0x01
to 0x05, then the half-step rates 0x09 to 0x0C. **0x06 to 0x08 are NA** and the
firmware rejects them.

`0x04` is the shipped default, not `0x05`: the 25 % longer pulse switches the
ink visibly harder, and at drive 5 that is 60.5 ms / ~15 fps against drive 8 at
`0x05`'s 72.6 ms / 13.0 fps. Faster *and* darker, which is why fr and drive have
to be chosen as a pair.

Note what this rules out: the period does **not** scale with gate count. 200
lines here against 272 on the 5.79" gives the same 8.06 ms, so a smaller panel
buys no waveform time at all. See §6.

### The two costs that are not frames

| what | cost | how to avoid it |
|------|------|-----------------|
| **EOPT `0x3F` = `0x22` (POR)** | **+40.25 ms on every update** | write `0x3F = 0x07` |
| analog ramp — b6 in the activate byte | **+91.2 ms** | hold the rails up, ramp once |
| ramp down — b1+b0 | +141 ms | never per frame |

EOPT `0x22` is two discharge *scan frames*. On the 5.79" the same register cost
+17 ms; on a 200-gate panel it is 40 ms. It is POR, so **every stock driver on
this part is paying it**, and it is one register write to remove.

Measured, FR `0x05`, activate `0x0C`, null LUT:

| EOPT | slope | intercept |
|------|-------|-----------|
| `0x22` POR | 8065 us/frame | 48339 us |
| **`0x07`** | 8064 us/frame | **8088 us** |

Slope untouched, 40251 us gone. It was pure discharge scan.

## 2. `0x22` is a bitfield here too

| bit | meaning |
|-----|---------|
| 7 | enable clock |
| 6 | enable analog |
| 5 | load temperature value |
| 4 | **load LUT from OTP** |
| 3 | LUT/mode select (mode 1 vs mode 2) |
| 2 | **DISPLAY** |
| 1 | disable analog |
| 0 | disable clock |

Activate-byte scan, null LUT at 8 frames, EOPT `0x07`:

| activate | busy | meaning |
|----------|------|---------|
| `0x04` | 72595 us | display only |
| **`0x0C`** | **72597 us** | display, mode-2 select |
| `0x84` | 72594 us | + clock |
| `0x8C` | 72599 us | + clock, mode 2 |
| `0xC4` | 163845 us | **+ analog ramp, +91.2 ms** |
| `0xCC` | 163848 us | same |
| `0xCF` | 305033 us | + ramp down, +141 ms |

All four rails-up bytes are identical to within 5 us. With a custom LUT resident,
b3 and b7 make no observable difference — there is only one LUT in RAM.

**b4 discards a custom LUT.** `0x1C` and `0xFC` both carry it, so both reload the
OTP waveform. This is the SSD1683's `0xDC` trap in a different costume. Run a
custom waveform with `0x0C` or `0x04` only.

### What the OTP sequences cost, for reference

| seq | busy | what it is |
|-----|------|------------|
| `0xF7` | 2132 ms | mode-1 full refresh |
| `0xFC` | 458 ms | mode-2 partial, brings its own rails + temperature |
| **`0x1C`** | **363 ms** | mode-2 partial, rails already up. The shipped default. |
| `0x0C` | 362 ms | reuses the resident LUT — 1895 ms straight after a full refresh, because that leaves the mode-1 LUT resident |

`0xFC` − `0x1C` = 95 ms, and the streamed-fps difference between them measured
91 ms. Both agree with the 91.2 ms ramp in the scan above: three independent
routes to the same number.

Back-solving the OTP partial against the law: 363 ms ⇒ **~44 frames**. That is
what the vendor waveform spends.

## 3. LUT format — 153 bytes to `0x32`

```
bytes   0..59    VS levels — 5 blocks x 12 group bytes
                 one byte per GROUP, 4 phases at 2 bits: [7:6]=A [5:4]=B
                 [3:2]=C [1:0]=D
bytes  60..143   12 groups x 7 bytes  (see order below)
bytes 144..149   FR — 4 bits per group, two groups per byte
bytes 150..152   XON — 2 bits per group
```

Voltages are **not** in this block: `0x03` VGH, `0x04` VSH1/VSH2/VSL, `0x2C`
VCOM, `0x3F` EOPT. Write them individually.

### The group byte order is TP-FIRST

```
[0] TPA  [1] TPB  [2] SR_AB  [3] TPC  [4] TPD  [5] SR_CD  [6] RP
frames = (RP+1) * ( (SR_AB+1)*(TPA+TPB) + (SR_CD+1)*(TPC+TPD) )
```

The SSD1680-family figure was right and the SSD1683's RP-first reading does
**not** carry over. Settled by `bytescan` (section 1) — a full FR sweep under an
assumed RP-first order also produced a clean linear fit, so a slope that looks
right is not evidence that the layout is right. Only per-byte perturbation
separates them.

### Block order

`0` = LUTC (VCOM), `1` = WW, `2` = BW, `3` = WB, `4` = BB — same as the
SSD1683. So the two CHANGING classes are **3 (ends black) and 2 (ends white)**,
and 1/4 must stay at zero or static content gets driven.

Driving 1 and 2 by mistake pushed every unchanged white pixel toward black and
wiped the test card to a uniform grey. That is what identified the convention;
see the custom-LUT glass capture from that session.

VS levels: `00` = VSS (no drive), `01` = VSH1, `10` = VSL, `11` = VSH2. For the
VCOM block, `11` = floating.

Total waveform length is the **maximum** over the five blocks — they share one
timeline, so adding phases to an otherwise-idle block is free.

TP is a whole byte here (0..255), not 6 bits: VS lives in its own array rather
than sharing the top two bits, which is the one place this part is roomier than
the SSD1683.

## 3b. Contrast against drive frames — measured on glass

Single-shot white to test card, custom waveform, FR `0x05`, POR rails, VCOM
`0x08`, EOPT `0x07`. Contrast is p90 minus p10 inside the calibrated active
area. Reference: solid white reads 141.0, solid black 31.7.

| drive | frames | busy | fps streamed | contrast |
|-------|--------|------|--------------|----------|
| 1 | 2 | 16 ms | — | **13** — below threshold, ink does not move |
| 2 | 3 | 24 ms | **34.5** | 114 |
| 3 | 4 | 32 ms | — | 116 |
| 4 | 5 | 40 ms | **22.2** | 116 |
| 6 | 7 | 56 ms | — | 116 |
| **8** | **9** | **72 ms** | **13.0** | **121** (saturated) |
| 12 | 13 | 104 ms | 9.1 | 121 |
| 16 | 17 | 137 ms | 7.0 | 121 |
| OTP `0x1C` | ~44 | 363 ms | 2.8 | 97 |
| OTP `0xF7` full | — | 2132 ms | 0.5 | 91 |

Two things worth keeping:

- **The custom waveform beats the OTP on contrast as well as speed.** 121 at
  72 ms against 97 at 363 ms. The vendor partial is not merely slow, it is
  worse.
- **Streamed fps tracks the law to within 3 %** at every point, so the panel is
  purely waveform-limited: SPI, USB and host encode all hide behind the drive.

### The metric had to be calibrated first, and this is the trap

A hand-picked camera crop scored contrast 93-100 for **every** drive count from
1 to 24 — it made an 8 ms drive look as good as a 200 ms one. The crop included
the white bezel and the card's dark border line, so p90 was plastic and p10 was
a border; the histogram never saw the ink.

Fix: difference a solid-white capture against a solid-black one and take the
bounding box of what changed. That is the active area, exactly
(the calibration difference capture), and `tools/panelshot.py` carries the
result. **Never eyeball this crop.** A metric that cannot tell 16 ms from 200 ms
will happily confirm any waveform you like.

### The first update after arming is weak

The first custom drive after `arm_wave()` measured contrast 55 where every
repeat of the identical setting gave 95. VCOM and EOPT only take effect on the
update *after* they are written. `setup()` now arms at boot; if arming mid-run,
throw the first frame away.

## 4. Projection — what a custom waveform buys

FR `0x05`, EOPT `0x07`, activate `0x0C`, rails held up. SPI is 5000 bytes per
plane at 20 MHz hardware = 2.0 ms; two planes 4 ms.

| total frames | busy | + SPI | fps | vs OTP 2.8 fps |
|--------------|------|-------|-----|----------------|
| 4 | 40.3 ms | 44.3 | 22.6 | 8.1x |
| **5** (the 5.79"'s video floor) | **48.4 ms** | **52.4** | **19.1** | **6.8x** |
| 8 | 72.6 ms | 76.6 | 13.1 | 4.7x |
| 11 (the 5.79"'s MODE 8) | 96.8 ms | 101 | 9.9 | 3.5x |
| ~44 (the OTP partial) | 363 ms | 367 | 2.8 | — |

**Measured today: 2.8 fps** streaming, at 357 ms/frame wall clock against a
363 ms waveform. The waveform is ~100 % of the budget; SPI, USB and host encode
are all hidden behind the drive by the pipelined loop (proved by chase 0 and
chase 2 measuring identically over 30 s).

Projected only — no custom *driving* waveform has been built yet. The numbers
above are the law applied to a frame count, not a picture on glass.

## 5. The non-destructive probes

Both are in the firmware and cost nothing to re-run. Use them first on any new
panel.

**`calib [fr]`** — build a LUT where one group runs `TP` frames with every VS
phase at `00`. Full time cost, **zero field across the pixel**, so the image
cannot change. Sweep TP, least-squares the slope (frame period) and intercept
(fixed cost). Repeat per FR code to prove byte 144 is honoured.

**`seqscan`** — same null waveform, fixed frame count, vary only the `0x22`
activate byte. The difference between rows is entirely power sequencing.

Both refuse activate bytes carrying b4, which would reload the OTP LUT and time
a different waveform. After either probe the resident LUT is the null table: it
drives nothing, and `white` or any b4 sequence restores OTP.

`wave1681_build_null()` is in `ports/ssd1681-154/firmware/wave1681.cpp`; `wave1681_frames()`
decodes a table under either order so the two can be compared.

## 6. What the smaller panel actually buys

Against the CrowPanel 5.79" (SSD1683, 792×272, 26,928 B/plane), which reaches
16 fps on video at its 5-frame MODE 4:

| | 5.79" | 1.54" |
|--|--|--|
| pixels | 215k | 40k (5.4x fewer) |
| frame period at FR `0x05` | 8.11 ms | 8.06 ms — **no gain** |
| SPI, both planes | 13 ms @ 40 MHz | **4 ms @ 20 MHz** |
| trail mask work | 4 ms | ~0.7 ms |
| 5-frame wall clock | 62 ms → 16 fps | **52 ms → 19 fps** |

Pixel count does **not** buy waveform time. BUSY has no content dependence and
does not change with a windowed write, because the gate scan is always
full-panel; and the period is a true frame-rate target, so 200 gate lines cost
the same as 272. Fewer pixels buys exactly two things:

1. **Transfer.** On the 5.79" SPI was 13 of 62 ms (21 %); here 4 of 52 ms
   (8 %). That is why this panel can actually *reach* the waveform-limited
   ceiling.
2. **Trail-chase headroom.** The mask ring is 5000 bytes instead of 27k.

So expect ~1.2x the 5.79", not 5x. The floor is impulse, and it is the same ink.

### The one lever neither panel has tried

`0x3A` dummy line period and `0x3B` gate line width set the line timing
directly, and **no firmware in this repo writes either** — `EPD_Init` sets
`0x01`, `0x3C`, `0x18` and the RAM window and leaves both at POR. The SSD1683
path had no equivalent. If the gate line width can be shortened, the frame period
drops below the FR floor, and that is the only route to beating the 5.79" by more
than the transfer margin. `EPD_WriteLineTiming()` exists; sweep it against
`calib`.

## 6b. Video is a different floor from a single transition — MEASURED

A single-shot white-to-card transition is the **best** case: it starts from
fully settled ink and gets the whole waveform to itself. Continuous video is the
worst: nearly every pixel changes every frame, so each gets one short partial
drive in a mostly random direction and may never complete.

Measured by streaming a synthetic sweep clip — a 400x400 half-width black
bar sweeping horizontally with wraparound, so **every frame is exactly 50 % ink
and every pixel transitions twice per cycle**. That matters: see the two metric
traps below.

| drive | busy | streamed fps | video contrast |
|-------|------|--------------|----------------|
| 2 | 24 ms | 34.4 | 93 |
| **4** | **40 ms** | **22.2** | **118** |
| 8 | 72 ms | 12.9 | 127 |
| 16 | 137 ms | 7.0 | 132 |

Single-shot at the same settings gave 114 / 116 / 121 / 121, so continuous video
costs real contrast at the fast end (drive 2: 114 to 93) and almost nothing from
drive 8 up. The curve is flatter than the 5.79"'s was.

**Drive 8 stays the shipped default**, but for a narrower reason than first
recorded: on solid-edged graphic content drive 4 is already 118 and 72 % faster,
while on *dithered photographic* video the moving content is visibly soft at
drive 4 (silhouette legible but grey at that drive).
That is the 5.79"'s finding intact: "a dithered photograph has no solid areas to
carry it". Pick by content:

- **drive 2, 34 fps** — high-contrast graphics only
- **drive 4, 22 fps** — solid-edged / graphic video
- **drive 8, 13 fps** — dithered photographic video. Default.

### Metric trap 2: static solid regions dominate p10

Streaming Bad Apple through a 4:3 letterbox reported contrast 127 at drive 4,
which looked like a great result. It was not measuring the video at all: the
letterbox bars are **static**, so they took one full transition and stayed solid
black, and p10 sat in those bars. The moving content was grey.

Use a full-frame pattern whose ink is all in motion. `sweepbar.mp4` exists for
exactly this. Any static solid area in frame will flatter a bad waveform.

### Metric trap 3: the first camera grab is cold

A cold ffmpeg open reads far too dark even with 40 warm frames — contrast 7-9
where the very next grab of the identical panel read 124-133. One such reading
was recorded as "Bad Apple at drive 4 is a washed-out ghost, contrast 15" and
drove a default choice before it was caught. `panelshot.py` now throws the first
grab away. **Never accept a single capture as evidence a waveform failed.**

Still open: trail chasing under the custom waveform. It is implemented
(`trail` / `chase`) and free on fps, but its effect on the soft-content case is
unmeasured. On the 5.79" it was what cleared stalled transitions.

## 7. Not yet done

- **Trail/chase under the custom waveform.** The remaining lever for the soft
  dithered-content case at low drive counts. Section 6b.
- **Trail chasing under the custom waveform.** Implemented but never measured
  here. On the 5.79" it was the fix for stalled black-to-white transitions and
  cost zero waveform time. `chase 0` and `chase 2` measured identically on fps
  (2.80 both, over 30 s), so the extra plane write is free — only the picture is
  unmeasured.
- **DC creep.** VCOM is already at `0x08`, the 5.79"'s fix for a short waveform
  darkening the whole panel. Not verified over a long run here: stream for
  several minutes, then `white1` and check the field is still clean.
- **Impulse headroom.** VSH1 `0x41` to `0x4B` (15 to 17 V) and VSL `0x32` to
  `0x3A` (-15 to -17 V) is ~13 % more drive at an identical frame count, both in
  spec. `volts 4B 3A` now parses (it used to read bare hex as decimal and reject
  itself). Untested — the obvious lever if the video floor lands high.
- **`0x3A` / `0x3B` sweep.** Section 6. Still untouched.
- **`reset_tp`.** Always 0 so far. The 5.79" needed it at 0 whenever trail
  chasing was on, because a re-driven pixel replays the opposite-polarity kick
  as a dark pulse behind the moving content.
